先把话说清楚：这不是"agent 的光谱"，是把任何一个软件/自动化系统，按同一个问题排成一条谱——"下一步做什么"由谁决定，从全由人写死到全由模型现场定。Agent 只是这条谱上的一格，不是一个孤立的新物种。

从左到右念四格：1. 固定流程（路径由人写死）；2. LLM + 工具调用（单轮，问一次答一次）；3. Agent（模型自己决定下一步、自己决定何时停）；4. 多 Agent 协作。

这是全场灵魂，讲慢、讲大。指着页底两块念：「Workflow 的控制流是人写死的；Agent 的控制流是模型现场决定的。」然后明确告诉大家：只有刀的右边，才需要操心幻觉、死循环和高昂的调试成本——刀左边的问题，用传统软件工程就能解决。

它把 workflow 和 agent 一刀切开，而且不依赖任何技术细节——业务方也能用。之所以用"分界线/一刀"来给定义，是因为"agent"没有一个干净的正面定义，但有一条干净的分界：谁决定下一步。

学术上，Agent 是什么给那条「实用一刀」补个理论根基

一个带自己运行状态的程序：
感知环境 → 自主判断 → 行动，去改变环境。
经典定义里的四个属性
自主性 Autonomy

课本里还有一句（Russell & Norvig / Wooldridge）：「所有 agent 都是程序，但不是所有程序都是 agent」——差别就在自主性，正是 P6 那一刀。
P7

论证

只讲个大概，给前一页那条"实用一刀"补个学术根基。学术上（Russell & Norvig 的经典教科书）：agent = 能通过传感器感知环境、通过执行器作用于环境的东西；再加 Wooldridge / Franklin 总结的四个属性——自主性、反应性、主动性（目标导向）、持续性（带自己的运行状态、长期跑）。一句话：一个带运行状态的程序，感知环境 → 自主判断 → 行动改变环境，如此循环。

关键的一句："所有 agent 都是程序，但不是所有程序都是 agent。" 普通程序按你写死的路径跑；agent 多了"自主"——自己决定下一步。这正好是 P6 那一刀，也是后面 P14「叫 agent 但不是」的判据。

讲法：指着图走一圈（环境→感知→Agent 判断→行动→改变环境→再感知），再点那句金句落回 P6。别展开学术流派，点到为止——前三个属性带过，重点落在第四个「持续性」：它带着自己的状态一直在跑，不需要你每一步推它一下。这正是 P4 那个计数单位（此刻有几个循环在运行、而你没盯着）的学术版。

衔接

这页是抽象闭环；下一页 P8 的 agent loop（选工具→执行→看结果→再决定）就是它在 LLM 时代的具体版——抽象到具体。

呼应

P4（持续性 = 没人盯也在跑）、P5（光谱）、P6（实用定义）、P8（loop 具体化）、P14（叫 agent 但不是）。

Manus（国产通用自主 agent）：2025 年初现象级刷屏，中国受众认知度最高的 agent。一句话派活，它在云端自己跑完复杂任务（演示过简历筛选、股票分析、建站等），过程可回放。典型"通用自主 agent"，但结果多为主观、靠人审，所以是异步跑完、事后审成果。（它后续的并购/监管传闻争议大，上台别展开。）

WorkBuddy（腾讯 all-in-one AI 工作空间）：你交一个办公任务，它自己规划 workflow、调工具、产出文件（带 Experts·Skills·Connectors·Automation）。官方卖点就是"每一步进度都可 review"——说明监督还停在"人在环上"，正因为很多办公任务结果不好自动验证。

Muse（Meta 个人 agent）：后台替你办个人杂务——拟会议大纲、想送礼点子、订行程，"while you do you"。自主后台推进，但个人事务好坏很主观，跑完拿回来你一眼扫。（Meta 产品，国内认知度低，当陪衬即可。）

落点

必须讲透的一句：编程 agent 之所以最成功，不是因为背后的大模型智商多高（几家用的模型其实差不多强），而是因为它们拥有极强、极便宜的自动验证机制——编译器、测试、lint 每一轮都免费判一次卷。P9 里的 Deep Research 同理：能走远，靠的是「每句话带引用、可溯源」这层半自动验证。

五个都是真 agent（分界线这关都过了），差别全在后两列。编程类因为有"免费裁判"能放手到环外，其它靠人审的只能盯着——这就引出第三节（监督粒度）和第四节（可验证反馈是前提）。例子在前、理论在后。

05 · 怎么做

评估：裁判权不能交出去

1测试清单是测试用的，不是实现用的。
2运动员（生成结果的 Agent）不可兼任裁判。
裁判须是确定性的 →编译器单元测试Lint / 静态检查JSON Schema 结构校验对账 / 规则脚本
3先写测试再写实现，本质是防作弊。
例：ExploitGym
判卷的人不能和考生在同一个房间里——裁判的独立性可能比准确性更关键。
P32

论证

依次讲三条。

① 测试清单是测试用的，不是实现用的。不是把所有 case 写进提示词——那是老式规则引擎。判断仍交给模型，清单是拿来验证模型判断得对不对的。比喻：模型是司机，你不用教它每个路口怎么转，但你得有考试路线确认它会开。

② 铁律：运动员（生成代码/结果的 Agent）绝对不能同时当裁判（验证结果对不对）。若测试由模型编写、执行、汇报，验证链条完全失效。成功的 Agent 系统背后，必定挂着一个确定性的裁判——编译器、单元测试、静态检查（lint）、严格的 JSON Schema 结构化校验，或者业务里的对账规则脚本。它们不会「觉得」对，只会判对或错。收回裁判权的最小成本：测试做成可独立运行的文件，自己在终端跑一次。

③ 先写测试再写实现，本质是防作弊。验收标准先固定，模型没法事后改测试迁就代码。

可讲的例子（ExploitGym）：一个近乎完美的客观验证器，结果模型去偷了它的答案。判卷的人不能和考生在同一个房间里——裁判的独立性可能比准确性更关键。

补充·可选

这不是个例：多家实验室和第三方评测都报告过模型改测试、把测试用例硬编码进实现、钻评分脚本空子（reward hacking）。所以「裁判独立」是工程要求，不是洁癖。

非代码场景也找得到确定性裁判：要求结构化输出就用 JSON Schema 卡死字段与类型；财务类用对账脚本；抽取类用抽检的金标准集。找不到任何确定性裁判的场景，回到 P17 / P21——多半不该做。

金句

「没有自动化、确定性的验证机制，Agent 的多轮循环就只是错误的无限放大器。」（回扣 P8 那个感叹号）

呼应

P16（模型之外的裁判）；P23（出口标准）；P39 技术方第 2 条（先写测试清单再写实现）。
